# 产品设计：廾匸转换

**状态：** 已确认，样本可行性验证进行中

**日期：** 2026-09-01
**版本：** 0.1

## 1. 产品摘要

廾匸转换是一个 Windows 本地工具。用户把 WPS 或 Microsoft Office 创建的标准 `.docx`、`.pptx`、`.xlsx` 文件拖入工具，选择输出目录，即可得到适合 Obsidian、文件系统知识库和 AI 上下文使用的 Markdown、图片资源和转换报告。

产品承诺的是“内容与结构可用”，不是“视觉版式无损复刻”。这是 Markdown 的能力边界，也是本项目避免误导用户的基本原则。

## 2. 问题与机会

个人办公文件中有大量可复用知识，但它们对知识库检索、Git 管理和 AI 读取并不友好。手工复制整理耗时，现有在线工具又会引入隐私和数据外流顾虑。

**How might we** 帮助个人用户在不离开本机、不手工重排大量内容的前提下，把常用 Office 文件变成结构清晰、可追踪缺失项的 Markdown？

## 3. 目标用户与核心任务

| 项目 | 定义 |
| --- | --- |
| 初期用户 | 希望整理个人知识资产、使用 Obsidian 或 AI 的 Windows 用户 |
| 主要任务 | 将已有文档、演示和表格转为可归档、搜索和引用的 Markdown |
| 当前替代方案 | 手工复制粘贴、在线转换网站、直接把原文件交给 AI |
| 成功体验 | 选择文件后得到可直接阅读的目录，用户只需处理报告中明确标出的少量例外 |

## 4. 产品原则

1. **本地优先。** 运行时不上传用户文件，不收集文档内容。
2. **语义优先。** 标题、文本、列表、表格、链接和图片比页面坐标更重要。
3. **透明降级。** 无法可靠转换的元素必须进入报告，不能静默忽略。
4. **可复用输出。** 输出使用普通 Markdown 和相对资源路径，不锁定某个知识库平台。
5. **单任务简单。** MVP 先把单文件转换做可靠，再考虑批量队列和自动化。

## 5. MVP 用户流程

1. 用户启动本地桌面应用。
2. 用户拖入或选择一个 DOCX、PPTX 或 XLSX 文件。
3. 应用显示文件类型、名称和输出目录选择器；用户确认开始转换。
4. 应用在本机解析文件、导出图片资源、生成 Markdown 和报告。
5. 用户查看完成摘要，并在文件管理器或 Obsidian 中打开输出目录。

不支持的文件、超出限制的文件或损坏文件必须在开始处理前给出可读错误信息，且不生成半成品输出目录。

## 6. MVP 功能需求

### 6.1 输入与安全

- 仅接受 `.docx`、`.pptx`、`.xlsx`，文件扩展名和 OOXML 内容均需校验。
- 用户一次转换一个文件；文件大小上限作为可配置本地限制，初始值待样本基准确定。
- 不执行宏、嵌入脚本、外部链接或文档中的活动内容。
- 临时解析文件在转换成功、失败或取消后清理；日志不得包含正文、单元格内容或图片。

### 6.2 Word 转换

- 输出文档标题、标题层级、段落、列表、引用、超链接和简单表格。
- 导出内嵌图片到 `assets/`，Markdown 使用相对路径引用。
- 未识别样式、浮动对象和复杂表格布局在报告中列出。

### 6.3 PowerPoint 转换

- 每张幻灯片成为一个二级标题段落，保留页码与标题。
- 提取文本框、项目符号、表格、图片和演讲者备注。
- 按视觉位置生成确定性的阅读顺序；当形状重叠、分栏或组合对象使顺序不可靠时给出警告。
- 动画、切换效果、SmartArt、音视频、图表和嵌入对象只报告，不承诺转换。

### 6.4 Excel 转换

- 为工作簿创建 `index.md`，每个非空工作表生成独立 Markdown 文件。
- 输出工作表名称、使用区域中的单元格显示内容、简单表格和已保存的公式文本。
- 合并单元格、隐藏行列、多区域布局、图表、透视表和无法取得的公式缓存值写入报告。
- 程序不计算公式，也不把旧缓存值标记为实时计算结果。

### 6.5 输出与报告

每次成功转换创建一个新的同名输出目录，除非用户明确选择安全的空目录。目录至少包含：

```text
<source-name>-markdown/
  index.md
  content.md | slides.md | sheets/
  assets/
  conversion-report.md
  source-manifest.json
```

- `index.md`：文件摘要与内部链接。
- 内容文件：实际转换后的 Markdown。
- `assets/`：图片等可安全导出的静态资源。
- `conversion-report.md`：统计、警告、跳过元素和可操作建议。
- `source-manifest.json`：来源文件名、格式、转换时间、工具版本、资源清单与警告代码；不记录原始正文。

## 7. 质量与验收标准

进入实现前，建立至少 12 个脱敏或自行构造的样本文件，每类格式至少 4 个，覆盖常见文本、列表、图片、表格和异常元素。

MVP 验收标准：

- 所有有效样本均能产生完整输出目录或明确失败原因。
- 目标元素在人工比对中可正确找到，图片相对路径可在 Obsidian 中加载。
- 不支持元素均出现在转换报告中；不允许“无警告丢失”。
- 运行时没有外部网络请求，临时文件在流程结束后不存在。
- 转换结果在相同输入下稳定，不因重复运行改变标题、资源名或顺序。

性能阈值在获得真实样本的文件大小与复杂度分布后确定；当前不虚构秒级指标。

## 8. 明确不做

- `.wps`、`.et`、`.dps`、`.doc`、`.xls`、`.ppt`。
- 扫描件 OCR、PDF 转换、图表数据重建、公式计算、宏与嵌入对象处理。
- 原稿视觉保真、PPT 动画还原、网页发布和在线协作。
- 批量队列、定时监控、云端同步和账户体系。

这些能力并非没有价值，而是它们会把 MVP 从“验证知识归档价值”变成“解决 Office 兼容性平台问题”。

## 9. 方案与技术边界

应用采用 Windows 原生桌面界面，解析核心和界面分离。原生界面能够可靠地调用文件与目录选择器，适合纯本地办公文件处理。解析层输出统一中间文档模型，Markdown 渲染层和资源导出层消费该模型。具体库版本必须在样本可行性验证后锁定。

这项选择使后续的 WPS 原生格式适配、批量处理、HTML 输出或 AI 清洗成为独立扩展，而不是重写三种格式解析逻辑。

## 10. 关键假设与验证方式

| 假设 | 风险 | 验证方式 |
| --- | --- | --- |
| 常见文件使用标准结构 | 样式、布局或对象不被库支持 | 用真实样本建立解析基准 |
| Markdown 足够满足归档与 AI 阅读 | 用户仍需频繁查看原稿 | 将结果导入 Obsidian 并完成实际检索任务 |
| 本地浏览器界面足够易用 | 安装、启动或路径选择体验差 | 用个人日常文件完成 3 次端到端操作 |
| PPT 坐标排序可读 | 分栏与重叠内容顺序错误 | 为典型版式建立人工审核的预期输出 |

## 11. 后续版本候选

- 批量转换与文件夹队列。
- WPS 原生格式的可选适配器。
- PDF/OCR 和表格导出策略。
- Obsidian 目录直接导入、YAML 元数据模板与 AI 摘要辅助。
- Windows 安装包与自动更新。

上述候选不构成已承诺范围；应以个人使用中的转换质量为依据逐项评估。
