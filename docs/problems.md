# Problems and Risks

## PR-001：Markdown 与复杂 Office 页面不等价

- 状态：已知设计限制。
- 根因：Markdown 是线性语义标记，不包含任意页面坐标、动画或嵌入对象模型。
- 处理：优先导出语义内容和静态资源，所有不能可靠映射的元素进入转换报告。
- 预防：使用真实样本的人工对照测试，禁止将输出宣传为无损还原。

## PR-002：Excel 公式值未必可取得

- 状态：待技术验证。
- 根因：OOXML 文件可能不含最近保存的计算缓存，解析库也不负责执行 Excel 公式。
- 处理：保存公式文本；缓存值缺失时明确报告，不生成伪造结果。
- 预防：测试样本覆盖有缓存与无缓存两种工作簿。

## PR-003：浏览器宿主与本地输出目录选择冲突

- 状态：已解决；ADR-003 已接受。
- 根因：浏览器基于安全模型限制任意本地目录写入，无法把输出目录选择作为跨浏览器可靠能力。
- 处理：推荐改用 Windows 原生桌面 UI，直接调用本地文件和目录选择器；核心保持与 UI 无关。
- 预防：涉及本地文件读写的产品流程，在设计阶段先验证宿主平台的权限模型与输出交付方式。

## PR-004：项目尚无独立 Python 环境与锁定依赖

- 状态：已解决。
- 根因：系统 `python` 与 `py` 命令均不在 PATH；虽然 Codex 受控运行时可导入候选库，但它不应作为项目可复现环境。
- 处理：已在项目目录创建独立虚拟环境，使用 `pyproject.toml` 声明依赖并以 `requirements.lock` 记录验证版本。
- 预防：在任何项目代码或样本生成前，建立项目本地环境和可复现依赖清单。
- 备注：样本清单使用 JSON，以 Python 标准库校验，不额外引入 YAML 解析依赖。

## PR-005：Tkinter 无法进入 Windows 分发产物

- 状态：已解决，Windows 分发产物已验证启动。
- 根因：PyInstaller 检测到当前 Python 环境的 Tcl/Tk 安装损坏并排除 `tkinter`，而桌面应用在启动时导入它；此外，直接以包内 `__main__.py` 作为入口会失去相对导入上下文。
- 处理：新增顶层绝对导入启动器，并将 UI 宿主替换为可随应用分发的 `PySide6-Essentials`；核心转换层保持无 UI 依赖。
- 预防：每次变更桌面运行时或入口后，必须等待 PyInstaller 的 `Build complete!` 与 `COLLECT` 阶段结束，再检查新 exe 时间戳、警告文件和实际启动结果；不得把错误对话框仍在显示时的进程存活误判为启动成功。

## PR-006：Qt 绑定 DLL 的目录布局不满足 Windows 加载器

- 状态：已解决，干净 Windows 分发产物已验证启动。
- 根因：PyInstaller 默认将 `shiboken6.abi3.dll` 放入 `_internal\\shiboken6`，但 `PySide6\\pyside6.abi3.dll` 由 Windows 加载器加载时只会在其自身目录及已注册目录中查找依赖，因而无法解析该 DLL，导致 `QtWidgets` 导入失败。
- 处理：构建脚本显式将 `shiboken6.abi3.dll` 作为二进制文件收集到 `_internal\\PySide6`；增加回归测试验证此打包规则。
- 预防：所有含原生扩展的桌面依赖都要检查直接 DLL 依赖与最终目录布局，且必须从干净 `dist` 目录启动验证。

## PR-007：Qt 分发链在当前环境无法稳定运行

- 状态：已解决，改用 Tkinter/Tcl-Tk 构建链。
- 根因：当前 Python 3.12 受控运行时缺少 Tcl/Tk；改用 Qt Essentials 后，即使补充 `shiboken6` 与 DLL 搜索路径，PyInstaller 分发产物仍无法加载 `QtWidgets`。该环境下 Qt 原生依赖链不具备可交付性。
- 处理：使用系统 Python 3.13.9（Tcl/Tk 8.6）创建 `.venv-tk`，恢复 Tkinter UI；PyInstaller 已收集 `_tkinter` 和 Tcl/Tk 数据，成品已实际创建主窗口。
- 预防：将“分发程序创建预期主窗口”作为桌面验收条件；若基础运行时不具备所需标准库资源，不以增加大型 UI 框架作为默认补救方案。

## PR-008：复杂 Office 内容尚缺真实回归证据

- 状态：已知风险，v0.3 规划处理。
- 根因：现有自动化测试主要生成合成的基础 DOCX、PPTX、XLSX 样本；项目内真实或进一步脱敏的复杂文件样本为零。
- 影响：无法以现有测试证明 PPT 多栏阅读顺序、Word 浮动对象或 Excel 多区域表在真实文件中可靠。
- 处理：先建立无敏感信息的能力矩阵与回归样本；未有证据的元素继续报告降级，不宣传为已支持。
- 预防：每项兼容性提升必须同时提交样本、结构断言、预期警告和验证日志更新。

## PR-009：批处理异常、相对链接和实时状态曾存在缺口

- 状态：已解决，2026-09-01。
- 根因：批处理仅处理少量预期异常；来源链接以固定父目录计算；UI 只接收最终汇总。
- 处理：每个批项均隔离未知解析异常并记录安全错误；以最终输出目录计算相对来源链接；批处理服务发布运行与完成事件，UI 在主线程实时更新。
- 验证：自动化覆盖未预期解析异常后续处理、嵌套 vault 相对链接和逐项事件序列。

## PR-010：PPTX 链接图片会中断整份转换

- 状态：已解决，2026-09-01。
- 根因：`python-pptx` 会将链接或无法读取的图片形状标识为 `PICTURE`，但访问其 `image` 属性时会抛出 `ValueError`；适配器未做降级处理。
- 处理：图片导出失败时记录 `PPTX_LINKED_IMAGE_UNSUPPORTED` 警告并继续处理其余内容。
- 验证：加入形状桩回归测试；真实 15 页 PPTX 完成解析和端到端转换，仅产生一条警告。

## PR-011：中文 PyInstaller 名称在 Windows PowerShell 中编码损坏

- 状态：已解决，2026-09-01。
- 根因：Windows PowerShell 将中文 `--name` 参数传递给原生命令时发生代码页转换，导致 PyInstaller 生成乱码目录和 exe。
- 处理：PyInstaller 固定使用 ASCII 内部名称 `OfficeToMarkdown`，构建完成后由 PowerShell 在文件系统层重命名为“廾匸转换”。
- 验证：构建脚本回归测试、完整 PyInstaller 构建、中文发布文件与 Tcl/Tk 运行时检查，以及主窗口标题验证均通过。

## PR-012：PPT 视觉导出依赖交互式 PowerPoint COM 会话

- 状态：已降级处理；受限命令行真实文件实测失败，仍待可用交互式桌面会话验证。
- 根因：PPTX 的页面 PNG/PDF 需由本机 Microsoft PowerPoint 渲染；自动化启动既要求 STA COM 套间，也要求宿主具有交互式 PowerPoint 会话权限。此前 PowerShell 启动参数未显式指定 STA；受限命令行宿主还缺少可用登录会话。
- 处理：视觉导出为显式选项，使用只读、禁用宏的 PowerPoint 自动化，并以 `powershell.exe -Sta` 启动导出脚本；失败时删除未完成视觉目录、移除索引链接并写入 `PPTX_VISUAL_EXPORT_FAILED`，Markdown 主流程继续完成。
- 验证：服务级成功与失败回归测试覆盖视觉目录、索引链接和降级报告；新增回归测试验证 PowerShell 启动参数包含 `-Sta`。2026-09-01 使用用户提供的真实 PPTX 在隔离目录中请求 PNG 与 PDF：Markdown 主流程完成，未生成视觉文件，报告包含 `PPTX_VISUAL_EXPORT_FAILED`；独立 COM 探针返回 `COMException`（HRESULT `-2147023584`）。STA 修复后在相同受限宿主复测，仍因宿主登录会话限制降级。两次生成的临时文件均已删除，源文件未修改。

## PR-014：WPS 演示与 PowerPoint 的 PDF 导出接口不同

- 状态：已解决，WPS 优先导出器已实施。
- 根因：WPS 演示 COM 可打开标准 PPTX 并导出页面图片，但不兼容 PowerPoint 的 `ExportAsFixedFormat` 方法。
- 处理：WPS 脚本改用 `Presentation.SaveAs(<PDF 路径>, 32)` 导出 PDF，页面 PNG 保持逐页 `Slide.Export`；WPS 失败后才尝试 PowerPoint。
- 验证：无敏感合成 PPTX 的端到端探针成功生成 1 份 PDF 和 1 张 PNG；26 项自动化测试、Ruff 和 Windows 分发构建均通过。探针文件已删除。
- 预防：不同 Office 兼容实现不得假设 COM API 完全相同；每个引擎须有独立脚本、打包检查和实际格式探针。

## PR-013：受限桌面会话生成的临时文件可能无法由构建帐户清理

- 状态：已记录，待受限会话自动回收。
- 根因：一次桌面会话验证以隔离帐户创建了无敏感测试输出，其 ACL 不授予当前构建帐户删除或取得所有权的权限。
- 处理：已确认目录只包含生成的测试 PPTX 与测试输出，未包含用户文件；未扩大权限或修改 ACL，避免影响工作区中其他内容。
- 预防：后续跨会话验证应在相同帐户和可清理的专用临时位置执行；无法清理时必须在交付中明确报告。

## PR-015：受控 Python 虚拟环境缺少 Tcl/Tk 运行时

- 状态：已解决，2026-09-02。
- 根因：项目原 `.venv` 基于受控 Python 3.12，`tkinter.Tk()` 无法定位 `init.tcl`；旧 `.venv-tk` 的启动器已损坏。跨 Python 版本复用原环境的 `lxml` 二进制依赖也会导入失败。
- 处理：使用本机 Python 3.13.9 创建 `.venv-ui`，按 `requirements.lock` 安装依赖并以可编辑方式安装项目；构建脚本、README 与架构记录均切换至该环境。
- 验证：`.venv-ui` 下完整测试 28 项通过、Ruff 通过，且真实 Tkinter 主窗口以 `1080x760` 创建并完成布局断言。
- 预防：桌面应用验收必须包括真实 GUI 运行时的窗口创建测试；测试临时目录显式置于项目 `work/`，避免权限上下文污染系统临时目录。

## PR-016：800px 窗口高度下的视觉附件行覆盖队列

- 状态：已解决，2026-09-02。
- 根因：初版 Canvas 布局将输出规则卡片高度固定为 234px，但 PPTX 视觉附件行绘制到了该卡片下方，且 54px 队列行无法在 `1280x800` 默认窗口与底部操作栏之间完整容纳四项。
- 处理：输出规则改为两列紧凑布局，卡片高度调整为 208px；队列从 494px 起始，改用 34px 双行信息行，并为默认高度保留 228px 队列区域。
- 验证：新增源码布局回归断言；真实 Tkinter `1280x800` 窗口创建、控件命中区与复选框交互冒烟检查通过。
- 预防：Canvas 固定布局修改必须同时校验默认窗口几何关系与演示队列的最小容纳高度。

## PR-017：文件夹扫描递归默认值的项目事实不一致

- 状态：已解决，2026-09-04。
- 现象：`docs/product-design.md` 与 `tasks/plan.md` 规定文件夹扫描默认不递归，但 `app.py` 使用 `tk.BooleanVar(value=True)`，当前运行界面默认包含子文件夹。
- 影响：直接按文档重构会改变现有运行行为；直接复制代码默认值会继续违背产品设计和验收计划。大目录场景还可能因默认递归意外加入大量文件。
- 根因：功能实现后的默认值变化没有同步回产品设计与任务合同，现有 UI 测试只验证开关存在和可切换，未断言初始值。
- 处理：用户已确认默认不包含子文件夹；将 `MainWindow.recursive` 初始值改为 `False`，并新增窗口初始化回归断言。
- 验证：聚焦 Tkinter UI 测试先以旧默认值失败，修复后通过；完整 pytest 与 Ruff 通过。
- 预防：所有用户可见默认值必须在状态单元测试中显式断言；改变默认值时必须同步产品规格和 CHANGELOG。

## PR-018：Windows 发布运行时在普通权限下不可启动

- 状态：已解决，2026-09-05。
- 现象：项目默认发布环境 `.venv-ui` 的 Python 启动器无法创建进程；其基准解释器 `C:\Users\27660\AppData\Local\Programs\Python\Python313\python.exe` 返回“拒绝访问”。
- 影响：普通权限下无法运行发布环境，会阻断本地桌面构建；提升权限运行时不受影响。
- 根因：Windows 对该 Python 3.13 安装目录的执行访问被系统环境拒绝；这不是项目源码或图标配置错误。备用 `.venv` 虽可运行测试和 PyInstaller，但绑定的受控 Python 缺少与其 Tcl 版本匹配的 `init.tcl`，不能作为 Tkinter 发布环境。
- 处理：保持发布脚本默认环境与既有已验证约定一致；使用提升权限的 Windows 运行时执行完整测试、`scripts/create-icon.py`、`scripts/build.ps1` 和 `scripts/package-installer.ps1`。
- 验证：完整 pytest 31 项通过，Ruff 通过；新 `dist\廾匸转换\廾匸转换.exe` 启动冒烟测试通过；新的 Inno Setup 安装包已生成，并验证安装包图标资源存在。
